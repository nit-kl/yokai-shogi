# 10. テスト戦略

## 現有テスト資産

| テスト | 内容 |
|---|---|
| `test/engine.test.ts` | エンジンの合法手、終局、ランダム自己対局の整合性 |
| `test/skills.test.ts` / `test/ssr-skills.test.ts` / `test/new-pieces.test.ts` / `test/hunger-ember.test.ts` | スキル、SSR体験、追加駒、飢餓の夜・残火の回帰テスト |
| `test/meta.test.ts` / `test/api-meta.test.ts` / `test/online.test.ts` / `test/match-hour.test.ts` | ローカル/APIメタ進行、オンライン報酬、逢魔が時 |
| `test/workers/*.spec.ts` | Workersランタイム上のAPI・D1・DO・パスキー統合テスト |
| `test/e2e/*.mjs` | Playwright実ブラウザ検証(オフライン・オンライン・日英) |

> 設計上の利点: エンジン・抽選ロジックが純粋関数的でNode上で完結するため、**最重要ロジックのテストが既に高速・決定的**。この性質(Web標準APIのみ・Node API非依存)を壊さないことをレビュー基準にする(Workersで動く条件でもある)。

## テスト基盤

- ユニット/統合: **vitest**
- Workersランタイム上のテスト: **@cloudflare/vitest-pool-workers**(API・DOをminiflare相当の実環境で実行。D1・DOストレージ・アラームも再現)
- 型チェック: `npm run typecheck` をCI必須(クライアント、サーバー、workersテスト用tsconfig)
- ブラウザE2E: playwright(既存資産を継続)

## テストピラミッド(リリース版)

```
        ▲ E2E(少数・重い)
        │   実ブラウザ2枚で wrangler dev 環境に接続し1局打ち切る
        │   ガチャ→編成→対戦→報酬の通し
        ├─ 統合(中)
        │   プロトコルテスト: WSクライアント×2 vs BattleRoom DO(vitest-pool-workers)
        │   REST APIテスト: 認証・ガチャ冪等性・編成検証・D1のbatch原子性
        ├─ ユニット(多数・高速)
        │   エンジン(既存)・抽選(既存)・レーティング計算・タイマー・検証ロジック
        ▼
```

## 重点テスト領域

### 1. プロトコル統合テスト(最重要)
nodeから素のWSクライアント2本を張り、シナリオを自動実行:

- 正常系: マッチ成立→交互着手→終局→報酬付与(DB残高まで検証)
- 不正系: 手番外の着手 / 非合法手 / 不正座標 / 高速連打 → すべて拒否されること
- 切断系: 片側切断→猶予内再接続→続行 / 猶予超過→切断負け
- 時間系: 時間切れ→自動投了(DOアラームはvitest-pool-workersで時間を進めてテスト可能な設計にする)
- 同時系: 両者同時メッセージ・終局直後の着手などレース条件
- 復元系: DO再起動(テスト内でインスタンス破棄)→ ストレージからの局面復元→続行

### 2. 決定性・再現性テスト
- 同一 `rng_seed` + 同一action列 → 同一イベント列(リプレイの根拠)
- `match_actions` の保存イベントと再計算イベントの一致検証(乱数注入の正しさの証明)

### 3. 経済トランザクションテスト
- ガチャ並列リクエスト(同一ユーザー×10並列)→ 残高負値・二重付与が起きない(条件付きUPDATE+batchの検証: doc 05)
- idempotencyKey再送 → 同一結果の再返却(新規抽選されない)
- currency_logs と残高の整合(doc 08 不変条件)を毎テスト後にアサート

### 4. クライアント・サーバー版ずれ
- 未対応のWSバージョンで接続した場合にハンドシェイクが拒否されること

## 負荷試験

- Cloudflare無料枠を保護するため、常時の自動負荷試験は実施しない
- stagingで2局同時成立・再接続・完走の接続スモークテストを行う
- 利用者増加またはPaidプラン移行を判断した時点で、予算上限を決めて負荷試験を再計画する

## カオス・例外系(手動+一部自動)

- 対局中のサーバー再起動(復元 or 補償フローの確認)
- DB一時停止中のAPI挙動(ユーザーへの適切なエラー表示)
- モバイル回線でのスリープ→復帰(WS再接続)実機確認: iOS Safari / Android Chrome

## テストデータ・環境の規約

- テストはすべて専用DB(マイグレーション→実行→破棄)。本番データを使ったテストは禁止
- 乱数を使うテストは必ずシード固定 or 統計的検定(現 meta-test の排出率検定方式を踏襲)
- playwrightテストは `data-testid` ではなく現行のid属性ベースを継続(小規模のため)
