# 03. オンライン対戦設計

## 対戦モード

| モード | マッチング | 報酬 | 備考 |
|---|---|---|---|
| ランダムマッチ | 逢魔が時の待機キューから自動 | 勝利チケット(上限あり→doc 08)、完走参加報酬 | 毎日20:00-22:00(JST)。初期はレートなし |
| フレンドマッチ | 6桁ルームコード | **報酬なし** | 勝ち譲り(win-trading)による報酬不正を構造的に排除 |
| ソロ(AI戦) | なし(ローカル完結) | 勝利チケット(上限あり) | オフラインでも動作 |

## 対局成立フロー

```
クライアントA            Matchmaker DO                クライアントB
   │ join_queue ──────────────▶│                          │
   │                           │◀────────────── join_queue │
   │                           │ ペアリング → BattleRoom DO生成│
   │                           │ 双方の編成をD1から取得・検証   │
   │◀───── match_found ────────│──────── match_found ─────▶│
   │  (相手情報・自分の手番・盤面初期状態・再接続トークン)            │
   │   以降は BattleRoom DO と直接WS接続                        │
   │◀───── game_start ─────────│──────── game_start ──────▶│
```

- **編成はサーバーがDBから読む**(クライアントから送らせない)。所持検証・大将1体検証は保存時(doc 04 `PUT /me/formation`)に済んでいるが、対局開始時にも再検証する
- 盤面の向き: サーバー内部では常に「先手=p / 後手=e」で正規化し、クライアント側で自分視点に描画変換する(現エンジンの p/e 構造をそのまま使う)
- 先手後手はサーバーがランダム決定

## 着手の進行(サーバー権威)

```
手番側クライアント        BattleRoom DO                    相手クライアント
   │ action {move/drop} ──────▶│                               │
   │                           │ 1. 手番・持ち時間検証             │
   │                           │ 2. Game.getAllActions で合法手検証│
   │                           │ 3. Game.applyAction(rng=サーバー) │
   │                           │ 4. 局面+actionログをDOストレージへ │
   │◀──── events[...] ─────────│───────── events[...] ─────────▶│
   │  (move/capture/promote/gameover… 現エンジンのイベント列と同形式)   │
                               │ 終局時: D1へ結果・棋譜・報酬を一括書き込み
```

重要な設計判断:

1. **乱数はサーバーで確定**: 会心(crit)などの確率スキルはサーバーが振り、結果をイベントとして配る。クライアントは演出するだけ。これにより「クライアントで乱数を引き直す」チートが不可能になる
2. **イベント列の形式は現エンジンの出力そのまま**: クライアントの `animEvent` / `animCapture` が無改修に近い形で流用できる
3. 不正な着手(非合法手・手番違い・時間切れ後)は `error` を返して無視し、回数をカウント(閾値超過で切断+調査ログ)

## 持ち時間

- 1手60秒 + 1局合計のストック時間はなし(シンプル先行。要調整)
- サーバーがタイマーの正本を持つ。残り時間は `your_turn` イベントに含めて送る(クライアント表示は近似でよい)
- 時間切れ: サーバーが自動投了処理 → `game_end {reason: 'timeout'}`

## 切断・再接続

```
切断検知(WS close / ping応答なし)
  → 相手に opponent_disconnected 通知(対局は持ち時間が進んだまま継続)
  → 60秒の再接続猶予(持ち時間と独立したタイマー)
       ├ 復帰: reconnect {token} → サーバーが現局面+残時間を再送(状態スナップショット) → 続行
       └ 猶予超過 or 持ち時間切れ: 切断側の負け {reason: 'disconnect'}
```

- 再接続トークンは match_found 時に発行(対局ID + ユーザーに紐づく短命トークン)
- スナップショットはBattleRoom DOのストレージから再送(**デプロイによるDO再起動・WS切断もこの同じ仕組みで吸収**される: クライアント自動再接続 → 復元局面の再送)
- 切断猶予などのタイマーはDOのアラーム機能で管理(休止状態からも正確に発火する)
- **放置対策**: 切断せず無操作の場合も持ち時間で自然に決着する

## マッチングアルゴリズム(初期)

1. キュー参加者を到着順に保持
2. キュー参加時と参加者変化時にペアリングを試行する
3. 初期は全ユーザーを単一キューに集約し、レート・地域・ルール別には分割しない
4. 逢魔が時以外のランダムマッチ参加は `MATCH_HOUR_CLOSED` として拒否する(`MATCH_HOUR_ENFORCE=0` の環境では開放可能)

レーティングはGlicko-2を採用予定(対局数が少ないプレイヤーの不確実性を扱えるため)。シーズン制と表示の詳細は doc 08。

## 観戦・リプレイ(Phase 4)

- actionログが対局の完全な記録になる(乱数結果込みのイベントも保存)ため、**リプレイは「イベント列の順再生」で実装可能**。現クライアントの演出パイプラインを流速変更付きで再利用する
- ライブ観戦は「ルームのイベントをread-onlyで購読」する拡張として設計(初期実装はしない)

## エッジケース一覧

| ケース | 処理 |
|---|---|
| 両者同時切断 | 双方に再接続猶予。両方戻らなければ無効試合(レート変動なし・報酬なし) |
| デプロイ・DO再起動 | DOストレージから局面復元+クライアント自動再接続で続行(無効試合にしない) |
| マッチ成立直後の即切断 | 成立後10秒以内の切断は不成立扱い(レート・報酬なし)。頻発ユーザーはペナルティ |
| 同一アカウント2接続 | 後勝ち(古い接続を切断)。同一アカウント同士のマッチは禁止 |
| 千日手・長手数 | 300手で引き分け(エンジンテストと同じ上限)。引き分けは報酬なし |
