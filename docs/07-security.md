# 07. セキュリティ・チート対策

## 原則: クライアントを一切信用しない

現プロトタイプは全データ・全計算がクライアントにあるため、オンライン化の本質は「**信頼境界をサーバーに引き直す**」こと。

| 対象 | 現状(プロトタイプ) | リリース版 |
|---|---|---|
| 盤面・着手の正当性 | クライアント計算 | サーバーが共有エンジンで検証・適用 |
| 乱数(会心等) | `Math.random` | サーバーが対局シードから生成し結果を配布 |
| チケット・妖力 | localStorage | DB+全増減ログ(currency_logs) |
| ガチャ抽選 | クライアント | サーバー(CSPRNG)+gacha_logs |
| 編成の所持検証 | クライアント | サーバー(保存時+対局開始時) |
| 勝敗・報酬 | クライアント | サーバーが終局判定し報酬付与 |

## チート手口別の対策

### 1. 改ざんクライアント・自作クライアント
- 前提: WSプロトコルは公開同然(難読化に頼らない)
- 対策: サーバーは「正規クライアントかどうか」を信用せず、**送られてくるactionの合法性のみ**で判断する。非合法手は無視+カウント、閾値で切断・対局没収

### 2. 有利な乱数の引き直し(リロール)
- 会心・ガチャの乱数はすべてサーバー。クライアントに「事前情報」を送らない(例: 次の会心判定を先送りしない)

### 3. ガチャの二重請求・レース
- `idempotencyKey` + DB一意制約(doc 05)
- 残高更新は**条件付きUPDATE**(`SET tickets = tickets - ? WHERE tickets >= ?`)で検証と更新を1文に畳み、ログ追記と同一 `batch()` で原子実行(D1にインタラクティブトランザクションがないための設計: doc 05)

### 4. 勝ち譲り・自演による報酬稼ぎ(win-trading)
- フレンドマッチは報酬なし(構造的対策)
- ランダムマッチ: 勝利報酬に日次上限(doc 08)+「同一相手との連続対戦」「異常に短い対局」「同一IP同士のマッチ」の検知ログ→閾値で報酬対象外
- ソロ(AI)戦の勝利報酬も日次上限(クライアント完結のため**ソロ勝利の申告は信用できない**。→ ソロ報酬もサーバー検証が必要だが、AI対局をサーバーで走らせるのは過剰。**ソロ報酬は「1日の上限を小さく」+申告制で割り切る**か、Phase 2以降でソロもサーバー進行に寄せるかを選ぶ。初期推奨: ソロは上限2枚/日の申告制+異常検知)

### 5. 長考・遅延による嫌がらせ
- 持ち時間で自然解決。加えて「直近Nゲームの時間切れ率」での一時マッチング制限

### 6. ボット(自動プレイ)
- 課金がないため動機は薄い(レート不正のみ)。初期は対策コストをかけない判断とし、レート上位の異常な指し手パターン検知(平均思考時間・AI一致率)をログだけ仕込んでおく

## アプリケーションセキュリティ

| 項目 | 対策 |
|---|---|
| 入力検証 | 全API/WSメッセージをスキーマ検証(zod等)。actionは座標範囲・型まで検証してからエンジンへ |
| SQLi | プレースホルダ必須(ORM/クエリビルダ経由) |
| XSS | 表示名等のユーザー入力は描画時エスケープ(現UIは `innerHTML` 組み立てが多いため、**ユーザー由来文字列を扱う箇所は `textContent` に統一**する改修を必須タスクにする) |
| CSRF | トークンはヘッダ送信(Cookie非依存)のため基本的に非該当。CORSはクライアント配信オリジンのみ許可 |
| CSP | `default-src 'self'` ベースで導入(現コードはインラインスクリプトなしのため適用しやすい) |
| 依存パッケージ | lockfile + 自動脆弱性スキャン(GitHub Dependabot) |
| シークレット管理 | 環境変数+ホスティングのシークレットストア。リポジトリに置かない |
| DoS | Cloudflare標準のDDoS防御+Rate Limitingルール+Turnstile(ゲスト発行)+WSメッセージレート制限(10msg/秒で十分。DO内でカウント) |
| ログの個人情報 | トークン・IPはマスク/ハッシュ化して記録 |

## 監査・調査の仕組み

- currency_logs / gacha_logs / match_actions で「いつ・何が・なぜ増減したか」を完全追跡できる(doc 05)
- 管理用の照会スクリプト(ユーザーの残高履歴を時系列表示)を運用ツールとして最初から用意
- BAN: users.status='banned'。対戦・ガチャAPIは即拒否。誤BAN解除手順も文書化

## 脆弱性対応プロセス

- 報告窓口(メール or フォーム)をサイトに明記
- 重大度判定 → 修正 → 影響ユーザーの特定(ログから)→ 必要なら補償・告知
- 四半期に1回、自分で脅威モデルの見直し(新機能追加時は必ず)
