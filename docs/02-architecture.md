# 02. システムアーキテクチャ

## 設計原則

1. **サーバー権威(Server Authoritative)**: 勝敗・通貨・ガチャに関わる計算はすべてサーバーで行う。クライアントは「表示と入力」に徹する
2. **エンジン共有**: ルールエンジン(`game.ts` + `data.ts`)はクライアント/サーバーで同一コードを使う。二重実装によるルール乖離を構造的に防ぐ
3. **Cloudflareにフルコミット**: 配信・API・リアルタイム・DB・バッチをCloudflareプラットフォームで統一し、運用コストと管理対象を最小化する(ロックインは受容するリスクとして明記。可搬性はエンジン・スキーマの独立性で担保)
4. **ソロプレイはオフラインでも動く**: AI戦はクライアント完結のまま残す(サーバー障害時もゲームの入口は生きる)

## 技術選定

| レイヤ | 採用 | 理由 / 注意点 |
|---|---|---|
| 言語 | **TypeScript で統一**(client / server / shared) | Phase 0の構造改修と同時に全面移行するのが最安。WSプロトコル・DB境界の型安全が最も効く。エンジンは約700行で移植コスト小、既存テスト資産が挙動の同一性を保証する |
| クライアント | Vite + TypeScript(フレームワークなし) | 現UIはバニラで完成度が高く、書き換えリスクに見合わないため構成は維持。Viteはビルド・型・ESM共有のためだけに使う |
| 静的配信 | Cloudflare Pages | 無料・PRごとのプレビューデプロイがレビューに効く |
| REST API | Cloudflare Workers + **Hono** | FastifyはWorkersで動かない。HonoはWorkers最適化・軽量・型フレンドリー |
| リアルタイム対戦 | **Durable Objects + WebSocket(Hibernation API)** | 「1対局=1オブジェクト」がターン制と完全に一致。状態の置き場所・スケール・地域分散が設計不要になる。Hibernationでアイドル接続のコストも抑制 |
| DB | **D1(SQLite)** | 本ゲームの規模・コストに最適。**制約: インタラクティブトランザクションなし** → 通貨処理は条件付きUPDATE+`batch()`の原子性で設計(doc 05) |
| バッチ | Cron Triggers | 日次の経済整合チェック・休眠ゲスト削除など |
| 設定・フラグ | KV | メンテモード・ゲーム内お知らせJSON |
| bot対策 | Turnstile | ゲストアカウント発行時の検証(doc 06) |
| 監視 | Workers Logs / Analytics Engine + Sentry(クライアント) | doc 09 |
| ローカル開発 | wrangler dev(miniflare)+ Vite | D1・DO・KVをローカル再現できる |

### Workers採用に伴う制約(設計に織り込む)

- Node API(fs, net等)は使えない → **共有エンジンはWeb標準APIのみで書く**(現エンジンは依存ゼロのため問題なし。この性質を維持することがレビュー基準)
- 乱数は `crypto.getRandomValues`(CSPRNG)を利用
- デプロイ時にDOは再起動され**WebSocketは切断される** → クライアントの自動再接続+DOストレージからの局面復元で吸収(doc 03)。メンテウィンドウは不要になる

## エンジン共有戦略(最重要)

現状 `prototype/js/game.js` / `prototype/js/data.js` はグローバル定義のJS。Phase 0で **TypeScript ESMモジュール**に移植する。

```
shared/             ← クライアント・Workers・DOの全てから import
  data.ts           (妖怪マスタ・型定義: YokaiDef, Skill, Rarity ...)
  game.ts           (エンジン: GameState, Action, GameEvent の型と純粋ロジック)
  validate.ts       (編成検証などクライアント/サーバー共用の検証)
client/             ← 現 prototype/js/(main, menu, effects, audio, ai)をTS化
server/
  api/              (Hono: 認証・ガチャ・編成・戦績)
  do/               (BattleRoom / Matchmaker Durable Objects)
  db/               (D1マイグレーション・クエリ)
test/
```

**移植時のエンジン改修(挙動は変えない)**:
1. `applyAction(s, action, opts)` の乱数を**注入式**にする(`opts.rand?: () => number`)。サーバーは対局シード由来のPRNG、クライアント(ソロ)は従来通り
2. `Game._uid` のようなモジュール内可変状態を `GameState` 側へ移す(1プロセス/1DOで複数対局を扱えるように)
3. 型付け: `GameState` / `Action` / `GameEvent` を定義し、**この型がそのままWSプロトコルの型になる**(doc 04)。`shared/` の型をクライアント・サーバー双方が参照することで、プロトコル乖離をコンパイルエラーで検出できる

## コード構成の原則(アーキテクチャスタイル)

教科書通りのクリーンアーキテクチャ(4層+全面的な抽象化)は採らない。ただし、その核心である**依存の向きの原則**は本設計の柱として採用する。

```
[ドメイン]      shared/ … game.ts(ルール)・data.ts(マスタ)・validate.ts(検証)・抽選ロジック
    ▲  依存はここへ一方向のみ。shared/ は何にも依存しない(Web標準APIのみ・I/Oなし・純粋関数的)
    │
[ユースケース]   server/api のハンドラ(ガチャ・ログボ等のフロー)、BattleRoom DO の対局進行
    │
[インフラ・UI]   Honoルーティング・D1クエリ・DOストレージ・KV / クライアントUI(main, menu, effects)
```

### 守るルール(絶対)

- **shared/ にI/O・環境依存を持ち込まない**(import可能なのはWeb標準のみ)。これがブラウザ/Workers/vitestで同一コードが動く生命線であり、PRレビューの必須チェック項目
- 依存は常に内向き(インフラ→ユースケース→ドメイン)。逆向きが必要になったら設計ミスを疑う

### やらないこと(過剰な抽象の禁止)

- リポジトリパターンの全面適用: DBはD1の1実装のみで、テストも vitest-pool-workers が実物相当を再現するため、モック用抽象の出番がない。薄いクエリモジュール(server/db/)で十分
- DIコンテナ・ユースケースクラスの儀式: この規模ではレイヤーを増やすほど変更コストが上がる
- クライアントUIの層分離: 完成済みのバニラUIを活かす方針のため、UIは実利優先のまま

### 抽象(ポート)を導入する基準

「**実在する2つ目の実装が現れたときに導入する。投機的に作らない**」。現時点で正当化される抽象は以下の3つだけ:

| ポート | 実装1 | 実装2 |
|---|---|---|
| `Meta` インターフェース | ローカル版(ソロ・オフライン) | API版(サーバー権威) |
| エンジンの乱数注入 `opts.rand` | クライアント乱数(ソロ) | サーバーのシードPRNG |
| `GameEvent` イベント列 | ローカルエンジン出力(ソロ) | WS経由のサーバー配信(オンライン) |

## 対局状態の持ち方

- 対局の正本は **BattleRoom DOのメモリ+DOトランザクショナルストレージ**
  - 1手確定ごとに「直近の局面スナップショット+actionログ配列+タイマー+乱数状態」を単一の `runtime` 行へ上書きする
  - 無料枠保護のため、通常着手のDOストレージ消費は `runtime` 更新1行+アラーム更新1行に抑える
  - デプロイ・クラッシュ・休止からの再開時はストレージから復元(=対局は壊れない)
- **終局時にD1へ一括書き込み**(matches + match_actions + 報酬付与)。毎手D1に書かない(書き込み頻度の抑制とレイテンシのため)
- 終局書き込みの失敗に備え、DOストレージ側の記録は「D1反映済みフラグ」が立つまで保持(再試行で整合)

## スケール方針

| 項目 | 方針 |
|---|---|
| 対戦 | DOが「1対局=1オブジェクト」で自動水平スケール。設計上の上限は実質なし |
| API | Workersは自動スケール。ステートレスを維持する |
| D1 | 単一DBの書き込みがボトルネック候補。終局時一括書き込みで頻度を抑える。将来必要なら「戦績ログ系を別D1へ分離」→「外部Postgres(Hyperdrive)」の順で検討 |
| 地域 | 初期は日本向け。DOのロケーションヒントで東京近傍に配置。グローバル展開時もDOモデルはそのまま通用する |

## クライアントの変更方針

- 画面遷移: タイトルに「オンライン対戦」を追加(ルーム作成/コード入力/ランダムマッチ)
- `main.ts` の対局進行を「ローカルエンジン直叩き(ソロ)」と「サーバーイベント受信(オンライン)」の2モードに分ける。**演出層(`animEvent`)はエンジンのイベント列をそのまま食べる設計が既にできている**ため、DOから同形式のイベントを送れば演出コードは共通化できる
- `meta.ts` は「ローカル版(ソロ用フォールバック)」と「API版」の同一インターフェース2実装にする(TSのinterfaceで強制)
