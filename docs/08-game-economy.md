# 08. ゲーム内経済・ガチャ設計

「**遊ぶほど集まる・サボると少し寂しい・不正しても旨味がない**」経済を作る。
コレクションはプレイ報酬だけで完走できる設計を維持し、**有償チケット・有償ガチャ・強駒バラ売りはしない**。

- **Web**: 任意のリワード広告視聴はプレイ報酬の延長として扱う(doc 22)
- **Steam**(計画): 広告なし。有料は **全駒解放DLC**(収集時短)と **異装等の見た目DLC** のみ(doc 23)。所持が増えても勝敗の主因は盤上の読みと編成であり、全所持は編成自由度の前倒しと位置づける

## 通貨一覧

| 通貨 | 入手 | 用途 | 上限 |
|---|---|---|---|
| ガチャチケット | ログボ・勝利報酬・配布・リワード広告 | ガチャ(1枚=1回) | 保有999 |
| 妖力 | ガチャ被り変換 | チケット交換(300→1枚) | 保有99,999 |

## 獲得設計

| 獲得源 | 量 | 上限・条件 |
|---|---|---|
| 初回登録 | 10枚 | アカウント(ゲスト)作成時に1回 |
| ログインボーナス | 1枚/日、7日連続ごとに3枚 | JST 04:00リセット(深夜プレイヤーの日付またぎ配慮)。連続判定もJST基準 |
| オンライン勝利(ランダムマッチ) | 1枚/勝 | **日次上限5枚** |
| ソロ(AI)勝利 | 1枚/勝 | **日次上限2枚**(申告制のため低め: doc 07) |
| ランダムマッチ参加報酬(完走・勝敗不問) | 1枚(土曜対戦会は2枚) | **1日1回**(participation_logs PKで担保)・最低10アクション(即投了対策)。キューは常時開放。土曜は限定妖怪を確定入手(初回のみ)。doc 18 |
| リワード広告(任意視聴) | 1枚/回 | **日次上限2回**(ad_reward_logs)。機能フラグで本番は初期オフ。doc 22 |
| フレンドマッチ | なし | win-trading対策 |
| 引き分け・切断勝ち | なし(参加報酬は対象) | 不正・事故の旨味を消す。参加報酬は勝敗不問のため win-trading 誘因にならない |
| 運営配布(補償・記念) | 都度 | currency_logs reason='compensation' で記録 |
| Steam 全駒解放DLC | 対象駒の一括所持 | チケット消費なし。`/v1/steam/dlc/sync` 後に `user_yokai` へ付与。無料ルートは残す(doc 23) |

> 週あたり標準獲得量: ログボ9枚 + 勝利報酬・参加報酬。オンライン勝利上限まで遊ぶ熱心なプレイヤーは週に複数回10連できる設計。コレクション完走後の余剰は妖力の追加用途で受け止める。
>
> Steam では広告報酬がないため、ログボ・対戦報酬が Web と同等以上であることを維持し、「広告がない分だけ損」に見えないようにする。

## Steam DLC と経済の境界

| 売ってよい | 売らない |
|---|---|
| 全駒解放パック(現行ガチャ排出駒の一括所持。価格目安 ¥800〜¥1,500) | 有償ガチャチケット |
| 異装・テーマ・BGM 等の見た目 | 強駒のバラ売り |
| (将来)拡張パック※新駒はプレイ入手経路も同時に用意 | Pay-to-Win の必須課金要素 |

### 全駒解放の同期(実装骨格)

- DLC ID: `full_collection`(`shared/steam-dlc.ts`)
- `POST /v1/steam/dlc/sync` が `GACHA_POOL` を `user_yokai` へ冪等付与し、`steam_entitlement_grants` に記録
- 開発: `STEAM_AUTH_MOCK=1` 時のみクライアント申告(`dlcIds`)を信頼。検証は `?steamDlc=full_collection`
- 本番: Steam 所有確認に差し替え予定(未確認時は付与しない)

### 新駒追加時のルール(仮)

1. 新駒は Web / Steam 双方でプレイ入手可能にする(ガチャプールやイベント)
2. 全駒解放DLC購入者は、対象範囲の新駒を即時所持できるようパック定義を更新する(または後継パックを出す)
3. イベント限定駒(`limited`)をパックに含めるかは個別判断。原則はガチャ排出対象を主対象とする

## ガチャ仕様

- 排出率: **N 40% / R 40% / SR 16% / SSR 4%**(SSRのうち異装全体で0.5%)
- 10連: SR以上1枠確定(全枠N/Rの場合、最終枠をSR 80% / SSR 20%で引き直し)
- 被り: 妖力に自動変換(N20 / R50 / SR150 / SSR400)
- プール: `shared/data.ts` の `GACHA_POOL` が正本。限定妖怪2体(`nurarihyon_hyakki`・`kyubi_hasha`)を除く全種が対象(56種中54種)

### 天井(Pity)の導入検討 — Phase 3

- 累計100回引いてSSR未入手なら次のSSRを確定付与(カウンタはSSR入手でリセット)
- 必要テーブル: user_profiles に `pity_count INT`
- 全SSR所持済みプレイヤーには無意味なため、「未所持SSR優先排出」もセットで検討

## コレクション完走後の体験(エンドコンテンツ)

被り→妖力→チケット→被り…のループは完走後に意味を失う。Phase 3以降で以下のいずれかを足す:

1. **限定スキン**(色違い・成り演出差分)を妖力で交換 — 実装コスト低、make-variantsの仕組みを再利用可
2. シーズン新妖怪の追加(2〜3ヶ月ごとに2〜4種)
3. 妖力→「編成スロット追加(編成プリセット保存枠)」等の利便性交換

## レーティング・シーズン(Phase 3)

- Glicko-2(初期 rating 1500 / RD 350)
- シーズン: 3ヶ月。終了時にレートをソフトリセット(1500方向へ50%圧縮)
- シーズン報酬: 到達帯に応じたチケット+称号(表示のみ)。**報酬はマッチ参加数の最低ライン(例: 10戦)を条件**にして放置勢の受け取りを防ぐ
- ランキング表示: 上位100名(表示名のみ。doc 11のプライバシー方針に従う)

## SSR体験(月齢・覚醒・因縁共鳴)

SSRを「数字が大きいだけの駒」から「使っていて楽しい駒」へ。会心の運任せを「狙って出す」に置き換え、期待値は改修前とほぼ同等に保つ(Pay-to-Win化させない)。ルールは `shared/game.ts` が正本、対局記録の `RULE_VERSION` は `phase2-v8`。

### 現行のSSR役割(駒ごとのスキル)

| 妖怪 | スキル | 概要 |
|---|---|---|
| 九尾の狐 | **moon** | 満月の手番は会心確定(それ以外は不発) |
| 酒呑童子 | **crit** | 会心20%×2。因縁共鳴「鬼の宴」で会心率+15pp |
| 玉藻前 | **charm** | 取った駒をその場で味方にし、元マスへ戻る |
| 茨木童子 | **recall** | 取られても自軍の持ち駒に戻る |
| ぬらりひょん | **legion** | 盤上の味方×+5%(上限+40%) |
| 八岐大蛇 | **hydra** | 取られても隣接へ最大2回逃げる。大将は取れない |
| がしゃどくろ | **famine** | 飢餓の夜に与ダメ倍率+回復 |
| 宿儺 | **dual** | 取ったあと隣接の別敵(大将以外)を追撃。2体目はダメージ半分 |
| 隱神刑部 | **veil** | 取ったあと残留 / 帰影 / 影遁を選択 |

- 月齢: 1夜=2手(両者1手ずつ)、**4夜周期**の4夜目が満月。盤の脇に月齢と「満月まであと何夜」を常時表示し、両者が満月を巡って読み合う
- 砂かけ婆(jam)は crit / moon / heads を封じる。legion は封じられない代わりに軍勢を削れば弱る
- 異装は spread 継承のため自動で同性能(性能同一ポリシー維持)

### 覚醒ゲージ(SSR必殺技・1局1回)

- 駒の取り合い1回ごとに**両陣営**のゲージ+1(6で満タン。win-trading的な非対称性なし)
- 満タンで手番を消費して自軍の盤上SSRを「覚醒」: **自分の手番3回のあいだATK×1.5**+専用演出(覚醒技名は駒ごと、異装は専用名)
- 手損と引き換えのため競技バランスへの影響は限定的。SSR非所持でも大将(九尾/酒呑=初期SSR)で全員使える
- サーバー検証は共用エンジンの `getAllActions` 経由で自動担保(`{ kind: 'awaken', to }`)

### 因縁共鳴(伝承ベースのペア。異装も同一扱い)

| ペア | 名 | 効果 |
|---|---|---|
| 酒呑童子×茨木童子 | 鬼の宴 | 両者盤上で酒呑童子の会心率+15pp(20%→35%) |
| 九尾の狐×玉藻前 | 妖狐相伝 | 片方が取られると残りが激怒: 次の攻撃が確定会心(一撃で解除) |

- 「このSSRを引いたから相方も欲しい」というガチャ動機と、編成の遊び筋を同時に作る
- スキル通算発動回数はローカル記録(`records.ts`)して図鑑詳細に表示(サーバー同期なし)

### 進行中対局との互換

`plies` / `awaken` を持たない旧スナップショットは `Game.ensureMeta` が初期化する(デプロイ跨ぎの対局も継続可)。

## バランス調整の運用

- 妖怪のステータス・スキル数値は `shared/data.ts` が正(デプロイで反映)
- 調整の根拠データ: matches から「妖怪別の編成採用率・勝率」を週次で集計するクエリを用意
- 調整基準(目安): 採用率60%超 or 勝率55%超が2週続いたら弱体化候補、採用率5%未満が続いたら強化候補
- ナーフ時の補償はしない(有償ガチャがないため不要と整理。告知は丁寧に行う。DLC 購入者にも性能保証はしない旨をストア文言で明示する)

## 不変条件(経済の健全性チェック)

日次バッチ(Cron Triggers)で以下を検証し、違反があればアラート:

```
1. user_profiles.tickets == 初期値 + Σ currency_logs.delta (tickets)
2. user_yokai の件数増加は gacha_logs の new_count 合計
   + 参加報酬の新規付与数 + 百鬼1位報酬の yokai_new 合計
   + steam_entitlement_grants.yokai_new 合計 と一致
3. 日次の勝利報酬付与 ≦ 上限 × アクティブユーザー数
4. gacha_logs の レアリティ実測分布が理論値から大きく乖離していない(乱数バグ検知)
```
